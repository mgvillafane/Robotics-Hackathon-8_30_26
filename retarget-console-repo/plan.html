Human-to-Arm Pipeline

v1.0 · packaging line demo
video → pose → retarget → sim + hardware

Architecture and build plan for the interface that ties a worker's packaging-line footage, MediaPipe extraction, and the WebGL simulation of your actual arm into one tool — with the sim's own parameters (joint limits, speed, mounting offset, payload weight) exposed as live controls.

revision · scope The physical arm demo is kept but deprioritized for this pass (still in §3/§5 as an optional relay). The current priority is the loop in the title: upload → MediaPipe → retarget → your simulated arm, with a parameter sandbox layered on top so the sim can be interrogated, not just replayed. See §3.5 for what "playing with parameters" means concretely.

01  Feasibility

—Yes, and the hard part is already identified

Everything you've described is a well-trodden shape in robot learning: video → human pose estimation → motion retargeting → robot execution, sometimes called learning-from-demonstration or visual imitation. MediaPipe for extraction and a WebGL rig for simulation are both proven choices. Nothing here requires new research to get a demo working end to end.

The genuinely hard part is not the interface — it's retargeting: mapping a human arm's landmarks (more degrees of freedom, different proportions, a camera-relative coordinate frame) onto a 6-axis industrial arm's joint space. Treat that as its own subsystem with its own owner, not a detail inside the UI. The plan below scopes a first pass (geometric IK + smoothing) that's enough for a convincing demo, with room to grow into the actual optimization work later.

The three teams (extraction, simulation, hardware) can build in parallel right now if they agree on one thing first: the joint-trajectory file format in section 3. That contract is what lets the interface below connect to all three without waiting on any of them to finish.

02  System shape

—Five pieces, one clock

The interface you're asking about isn't really "one interface embedding three others" — it's an orchestrator that owns a single clock (the video's playback position) and pushes the same per-frame data to two independent consumers: the simulation, over postMessage, and the physical arm, over a WebSocket relay. Neither consumer needs to know the other exists.

03  Subsystems

—Ownership and contracts

Each row is buildable and testable in isolation once the file format between rows 2 and 4 is agreed. That agreement is the actual unblocking step — more valuable to lock down this week than any UI code.

01

Perception · MediaPipe group

Runs MediaPipe Pose (or Holistic) over the mp4 offline in Python. Output: 33 landmarks per sampled frame, at a fixed rate (recommend resampling to a flat 30 fps regardless of MediaPipe's native rate, so nothing downstream has to handle variable timing).

02

Retargeting & optimization · the "ML algorithm"

Converts human landmarks into the target arm's joint angles: geometric IK from shoulder/elbow/wrist vectors first, a smoothing filter (One-Euro or Savitzky–Golay) to kill jitter, then joint-limit clamping. "Optimized" — shorter cycle time, less wasted motion — is a second pass on top of this once the direct-mapping version is demoed and validated.

03

Orchestrator UI · this build

Browser page. Plays the source video, reads the trajectory file, and on every frame pushes the current joint angles to the simulation (and, optionally, the hardware relay), keyed to video.currentTime — never to its own timer. See the working prototype delivered alongside this plan.

04

Scenario parameter layer · current priority · lives inside the orchestrator

Sits between the trajectory file and everything downstream. Takes the raw retargeted angles for the current frame and applies, live, in the browser: per-joint angle limits, a max joint-speed cap, a base mounting-offset, and a payload-weight heuristic. Nothing here touches the source video or the retargeting output — it's a lens on top of them. Formulas in §3.5 below.

05

Simulation · your exact arm model · already built

Embedded as an <iframe>. The only change it needs is ~15 lines: a message listener that reads {type:"pose-frame", angles} (the parameter layer's output, not the raw retargeted trajectory) and drives the existing rig. No rebuild, no shared codebase with the orchestrator.

06

Arm relay · hardware owner · optional, deprioritized

A small local service (Python or Node) on the machine wired to the arm, using its vendor SDK or serial protocol. Exposes a WebSocket the orchestrator connects to; owns rate limiting, its own hard joint-limit clamping, and the e-stop. The browser never talks to the SDK directly. Kept in the interface as a panel, not required for the current milestone.

3.5  What "playing with parameters" computes

Deliberately a heuristic, not a physics engine — fast to build, easy to reason about, and honest about what it is. Applied to the raw angles [base_yaw, shoulder, elbow, wrist_pitch, wrist_roll, gripper] every frame, in this order:

holding   = gripper_angle > 35                 // treat a mostly-closed gripper as "carrying"
droop     = holding ? weight_kg × 6 : 0        // deg, elbow sags under load
elbow'    = elbow + droop
wrist'    = wrist_pitch + droop × 0.6

base'     = base_yaw + mount_offset_deg          // where the arm is actually bolted down

for each joint:  clamp(angle, joint_min, joint_max)

max_speed = speed_slider_deg_s / (1 + weight_kg × 0.35)   // heavier → lower effective speed cap
applied   = rate_limit(target, previous_applied, max_speed, dt)  // slew-rate limiter

The slew-rate limiter is what makes speed and weight visible: when the retargeted trajectory moves faster than max_speed allows, the applied angle falls behind and catches up over subsequent frames instead of snapping — the same behavior a real controller shows when commanded faster than it can execute. Joint limits and speed cap are exactly the kind of thing you'd otherwise only find by testing against physical hardware; this lets you find them in the browser first.

The file format that unblocks everyone

This is the one artifact worth agreeing on before any other code is written. Version it from day one.

{
  "version": "1.0",
  "source_video": "packaging_line_04.mp4",
  "sample_rate_hz": 30,
  "joint_names": ["base_yaw","shoulder_pitch","elbow_pitch",
                  "wrist_pitch","wrist_roll","gripper"],
  "frames": [
    { "t": 0.000, "joint_angles_deg": [ 12.4,-30.1, 55.6, 0.0, 0.0, 20.0] },
    { "t": 0.033, "joint_angles_deg": [ 12.6,-29.8, 55.1, 0.2, 0.0, 20.0] }
  ]
}

Raw landmarks are optional cargo on each frame if you want the orchestrator to also draw the human skeleton overlay — useful for the demo, not required for driving the arm.

The two live contracts

ChannelDirectionMessageNotes
postMessage orchestrator → sim iframe {type:"pose-frame", t, angles, jointNames} Sim replies {type:"pose-ready"} once loaded so the orchestrator knows it can start sending.
WebSocket orchestrator ↔ arm relay same frame shape, JSON text Throttle to ~20–30 Hz regardless of render rate — the arm controller doesn't need 60fps and shouldn't get it.

04  Build order

—Roadmap

0this week

Orchestrator + parameter sandbox, sample data

Build the interface, including the scenario parameter layer (limits, speed, base offset, weight), against a hand-written sample trajectory. Validates the sync architecture and the postMessage contract before either other team has to deliver anything. This is the prototype delivered with this plan.

1next

Real extraction, real skeleton

Swap in the MediaPipe group's actual landmark output from an uploaded dataset video. Confirm the overlay tracks the video with no visible lag or drift.

2next

Retargeting v1

Geometric IK + smoothing turns landmarks into joint angles for your actual arm's joint space. This is the raw trajectory the parameter layer then sits on top of.

3next

Swap in the real simulation

Point the iframe at your actual WebGL sim's URL. One integration session to align on the postMessage contract — not a rebuild on either side. The parameter sandbox now drives your real arm model, not the reference rig.

4stretch

Hardware relay, bench test

Deprioritized for now, kept as a panel in the interface. Stand up the local relay service and bench-test with conservative soft limits whenever it becomes the priority again.

5stretch

Live mode

Swap the pre-recorded file for a streaming webcam feed once replay mode is reliable. Optional — see risk on demo reliability below.

05  Risks

—What actually breaks this

RiskMitigation
Human and robot don't share a coordinate frameFix the camera mount and do a one-time calibration transform rather than solving general camera pose.
Human arm has more effective DOF than a 6-axis armScope retargeting to the joints the packaging task actually needs — reach, grasp, place — not a full-body map.
Sim, video, and hardware drift out of syncOne clock only: everything reads video.currentTime. Nothing downstream runs its own timer.
Raw retargeted angles sent straight to servosRelay always clamps to joint limits and owns the e-stop. Browser never talks to the SDK directly.
Live pipeline fails mid-pitchPre-recorded replay is the default for the demo (already decided). Live mode is a phase 5 stretch goal, not the fallback.
Mismatched frame rates across stagesResample the trajectory file to a fixed rate in the retargeting step, once, so every consumer gets uniform timing.

07  Demo

—Script for the pitch

  1. Upload a packaging-line clip from the dataset and hit play.
  2. Skeleton overlay traces the worker's motion in sync with the footage.
  3. The simulated arm mirrors the same motion on the same timeline, running your actual arm model.
  4. Live close: drag the payload-weight slider up and watch the arm visibly slow and droop while carrying; tighten a joint limit and watch the motion clip to it in real time.
  5. Optional, if hardware is wired up by then: connect the relay panel and show the physical arm following along.
